# 基层临床助手统一架构

## 页面树

```text
基层临床助手
├─ 首页（统一搜索、最近使用、核心模块）
├─ 用药助手
│  ├─ 搜索 / 分类 / 全部药物
│  ├─ 药品详情
│  ├─ 相互作用 / 禁忌
│  └─ 本院药库（病房 / 门诊 / 抢救车）
├─ 急救诊疗
│  ├─ 按主诉/危险征象进入
│  ├─ 急救流程
│  └─ 流程中的药品链接（drug_id）
├─ 临床工具（后续）
│  ├─ 计算器
│  └─ 常用医嘱
└─ 我的
   ├─ 收藏
   ├─ 笔记
   ├─ 待办
   └─ 数据导出与设置
```

手机底部导航固定为：首页、用药、急救、常用、我的。桌面端使用同一信息架构，不另建一套路由。

## 统一数据模型

### 公共数据

- `drug_concepts`：通用药物身份，例如阿司匹林、葡萄糖、肾上腺素；稳定主键 `drug_id`。急救流程只引用这一层。
- `drug_products`：院内具体品规，保存规格、剂型、厂家和现有目录 ID，并通过 `drug_id` 归属于一个通用药物身份。
- `drug_categories`：系统分类、药理分类及父子关系。
- `hospital_inventory`：具体品规在病房、门诊、抢救车的可获得性，通过 `product_id` 关联；不表达指南优先级。
- `emergency_protocols`：急救流程标题、版本、核验状态、来源和更新时间。
- `emergency_steps`：有序流程步骤。
- `emergency_drug_refs`：`protocol_id + drug_id + purpose + administration_context`，不复制药名或完整说明书。

现有病房 `drug-025`、门诊 `outpatient-*` 等 ID 暂时按 `product_id` 处理，不能直接作为急救流程的 `drug_id`。例如阿司匹林的多个病房/门诊品规应共同指向同一个 `drug-concept-aspirin`；急救流程引用该通用身份，页面再根据当前药库显示可用的具体品规。

### 个人数据

- `user_favorites`：`user_id + entity_type + entity_id`。
- `user_notes`：`user_id + entity_type + entity_id + content`。
- `user_tasks`：`user_id + title + status + due_at`。
- `user_settings`：每个用户独立的界面和默认药库设置。

患者身份信息不进入收藏、笔记或待办的默认数据模型；如未来确需处理，必须作为单独的合规项目评估。

## 账号与隔离

建议采用统一身份服务和数据库逐行权限：

1. 公共临床数据默认所有已授权用户只读，只有管理员/审核者可以修改。
2. 每条个人数据必须包含 `user_id`，数据库层强制只能访问当前登录用户的记录。
3. 管理员能维护公共资料，但默认不能查看其他用户的私人笔记。
4. 前端不持有管理员密钥；所有公共写操作通过受保护的后台或审核流程完成。
5. 首次登录时可选择把当前浏览器本地数据迁移到账号；迁移完成前保留 JSON 导出回退。

当前阶段不接入真实账号服务，只冻结上述边界并通过 `clinical-data-contract.js` 做前端契约检查。

## 分阶段实施

1. 已开始：稳定基线备份、统一首页/导航骨架、页面树和数据契约。
2. 下一步：在急救仓库为所有流程建立药名到 `drug_id` 的显式迁移表，并报告未匹配/多匹配项。
3. 再下一步：把急救页面作为统一站的内部模块路由，同时保留原急救站跳转回退。
4. 账号阶段：接入统一认证、个人表和逐行权限；执行本地数据迁移演练。
5. 稳定后：经自动检查与临床审核，通过 PR 合并；旧站至少保留一个发布周期。
